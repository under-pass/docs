The UnderPass Public API exposes a small, stable surface for white-label
integrators to build their own event landing and checkout. The full OpenAPI
3.0 spec is in this repo at [`api-reference/openapi.json`](https://github.com/under-pass/docs/blob/main/api-reference/openapi.json) — Mintlify renders one
page per endpoint automatically.

## Base URLs

| Environment | URL |
| --- | --- |
| Production | `https://api.underpass.com.co` |
| Development | `https://api-dev.underpass.com.co` |

All endpoints are prefixed with `/api`.

## Authentication

The endpoints in this reference are **public** — no bearer token required.
Identity is established at two layers:

1. **Tenant scoping** — `account_id` on `GET /events/public` filters to your
   tenant's events. Checkout endpoints scope implicitly through the
   `ticket_type_id` you pass (which belongs to an event, which belongs to
   your account).
2. **Session key** — reservations and waiting-room passes belong to an
   opaque per-browser `session_key` you generate (see
   [Reservations](/guides/reservations)). There is no API key on the public
   surface today; per-tenant keys for higher-trust integrations are on the
   roadmap, not something to send yet.

## Response envelope

Every successful response is wrapped:

```json
{
  "statusCode": 200,
  "message": "Request successful",
  "data": <your payload>,
  "timestamp": "2026-05-23T12:34:56.789Z"
}
```

Always read `data`. Errors use a different shape:

```json
{
  "statusCode": 404,
  "code": "EVENT_NOT_FOUND",
  "message": "Event not found",
  "detail": { "slug": "foo" },
  "timestamp": "2026-05-23T12:34:56.789Z"
}
```

Match on `code` (stable identifier) rather than `message` (subject to copy
changes).

## Rate limits

There is no per-IP throttle on the public routes at the edge: a storefront
behind a corporate NAT or a mobile carrier is not punished for sharing an
address. The gateway keeps a generous safety budget (on the order of
10,000 requests per minute per client) and answers `429` beyond it; if you
ever see one, back off with exponential delay and retry.

Admission control for a high-demand on-sale is the
[waiting room](/guides/waiting-room), not rate limiting: it meters buyers
per event at the rate the organizer sets, and polling it is cheap on both
sides (`poll_after_ms` tells you when to ask again). Please respect that
cadence, and poll `checkout/status` every 2 to 3 seconds at most.

## Idempotency

`POST /checkout/start` is **not idempotent** on its own. If you retry a
checkout, you create a second order. Use the returned `order_id` to track
which one is in-flight; show a "creating order…" state while the call is
pending and **don't auto-retry on timeout** — instead, fetch the order list
for the buyer's email or treat it as failed.

For the next major version we plan to support an `Idempotency-Key` header
to make safe retries possible. Until then, gate the submit button.

## What is in the reference

Events and seat maps (`/api/events/public/*`), reservations and the waiting room
(`/api/checkout/holds`, `/api/checkout/queue`), checkout and order status, and the promo-code,
sales-link and referral validators. Every field added after v1.0 is optional and opt-in per
event; see the [changelog](/changelog).

## SDK?

We don't ship a polished SDK yet — the surface is small enough that plain
`fetch` works well. TypeScript types are auto-generated from the OpenAPI
spec; we recommend [`openapi-typescript`](https://openapi-ts.dev/) to
generate types in your own repo:

```bash
npx openapi-typescript \
  https://docs.underpass.com.co/api-reference/openapi.json \
  --output ./src/lib/underpass-api.d.ts
```
