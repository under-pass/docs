<Note>
  This documentation is for **white-label integrators** who host their own branded event
  listing and ticket checkout while UnderPass handles inventory, orders, payments, tickets
  and settlement behind the scenes.
</Note>

## What you get

A small, stable HTTP API that covers the whole sales journey:

- **List events** for your tenant account and **render an event page** with localities,
  ticket types, selling stages, prices, dates and organizer info
- **Reserve tickets** the moment a buyer picks them, so nobody is sold a ticket that is gone
- **Sell seats** on numbered localities, with a public seat map and best-available fallback
- **Put buyers in a waiting room** for high-demand on-sales, without building a queue
- **Start a checkout** that redirects the buyer to a hosted payment page, with installments,
  promo codes, sales links, referrals, group tickets, attendees and bar perks
- **Poll the order** after payment to render a confirmation screen

You never handle payments, settlement, taxes, invoices or ticket delivery.

## How it fits together

Your frontend, in any framework, calls `https://api.underpass.com.co` over HTTPS. After a
buyer submits checkout you redirect them to the URL we return; they pay there (Bold or
ePayco, whichever the organizer configured) and land back on a URL you provide. You poll us
to render the confirmation page.

## The endpoints

### Core sales flow

| Verb | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/events/public?account_id=…` | List your tenant's published events |
| `GET` | `/api/events/public/{slug}` | Event detail: tickets, stages, prices, dates, organizer, pixels |
| `POST` | `/api/checkout/holds` | Reserve the buyer's selection ([Reservations](/guides/reservations)) |
| `GET` `PATCH` `DELETE` | `/api/checkout/holds/{id}` | Read, resize or release a reservation |
| `POST` | `/api/checkout/allowed-document-types` | Document types allowed for the cart's localities |
| `POST` | `/api/checkout/start` | Create the order, get the payment redirect URL |
| `GET` | `/api/checkout/status/{orderId}` | Poll the order after payment |

### Per-event features

| Verb | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/events/public/{slug}/seating` | Seat map and current occupancy ([Numbered seating](/guides/seating)) |
| `GET` | `/api/events/public/{slug}/seating/occupancy` | Occupancy only, for polling |
| `POST` | `/api/events/public/{slug}/seating/best-available` | Contiguous free seats for a ticket type |
| `POST` | `/api/checkout/queue` | Join the waiting room ([Waiting room](/guides/waiting-room)) |
| `GET` `DELETE` | `/api/checkout/queue/{id}` | Poll the place in line, or leave |
| `POST` | `/api/promo-codes/validate` | Validate a promo code; may unlock hidden selling stages |
| `POST` | `/api/sales-links/validate` | Validate a private sales link code |
| `GET` | `/api/referrals/program/{eventId}` | Public referral program for an event |
| `POST` | `/api/referrals/validate` | Validate a referral code |

Anything outside this list is not reachable from the public internet.

## Identity & scoping

Requests are scoped to your **tenant account UUID** (`account_id`), provided during
onboarding. There is no per-user authentication: buyers do not need accounts. Ticket type ids
on checkout endpoints implicitly scope to your tenant, because tickets belong to events that
belong to your account. Reservations and waiting-room passes belong to a **session key** you
generate per browser.

For higher-trust integrations (rate-limit increases, audit logging) we issue per-tenant API
keys, sent as `X-UnderPass-Api-Key`. Not required for the public surface above.
